This document instructs Google Antigravity to build a fully functional, self-hosted PHP agency panel that connects to the Meta Graph API, pulls ad performance data for each client, and renders per-client customizable dashboards. Each client has a unique login, a branded view, and can be given read-only or controlled access to their own data only.

2. Goals & Non-Goals

2.1 Goals
• Multi-client support — 50+ clients, each isolated, on a single codebase
• Meta OAuth — each client connects their own Ad Account via Meta Business Login, OR agency connects on their behalf via System User token
• Per-client dashboard customization — visible widgets, KPI cards, date range defaults, currency, report label — all configurable by agency admin
• Cron-based data sync — automatic data pull every 6 hours, cached in MySQL; no live API call on dashboard load
• White-label ready — agency can set logo, brand color per client portal
• Role system — Super Admin (agency), Client (read-only), Team Member (Tanisha / Kumkum with selective access)
• Hostinger-compatible — no composer packages that need root, no Node.js runtime; pure PHP + vanilla JS
• Export — CSV and PDF export of any date range from dashboard
2.2 Non-Goals (out of scope v1)
• No Google Ads / TikTok / LinkedIn in v1 — Meta only
• No real-time bid management or ad creation
• No Looker Studio or third-party BI dependency
• No Docker or VPS setup — must work on shared hosting

5. Meta Graph API Integration

5.1 App Setup (Agency does this ONCE)
• Create a Meta App at developers.facebook.com → Business type → enable "Marketing API" product
• App ID and App Secret → store in .env as META_APP_ID and META_APP_SECRET
• Set OAuth Redirect URI → https://panel.digitalrubix.com/oauth_callback.php
• Request permissions: ads_read, ads_management, business_management, read_insights
5.2 Client Onboarding Flow (OAuth)
• Admin goes to client_edit.php → clicks "Connect Meta Account"
• System redirects client (or agency on their behalf) to Meta OAuth dialog with above scopes
• Meta redirects to oauth_callback.php with short-lived token
• System exchanges it for a long-lived token (60-day expiry) via /oauth/access_token endpoint
• Token encrypted with AES-256 → stored in clients.meta_access_token
• System calls /me/adaccounts to get their act_XXXXXXXX → stored in meta_ad_account_id
5.3 Data Pull — Graph API Calls (in meta_api.php)
GET /{ad-account-id}/insights
  ?fields=campaign_name,adset_name,ad_name,impressions,reach,clicks,
          spend,cpc,ctr,cpm,conversions,cost_per_result,frequency,
          action_values,actions
  &level=campaign          (loop for adset and ad too)
  &time_range={"since":"YYYY-MM-DD","until":"YYYY-MM-DD"}
  &time_increment=1        (day-by-day breakdown)
  &limit=500
  &access_token={client_token}
5.4 Token Refresh Strategy
• 60 days before expiry: cron job calls /oauth/access_token to get fresh long-lived token
• On API call failure with error code 190 (token expired): flag client in DB, send admin email alert
• Admin panel shows token health indicator per client (green/yellow/red)
5.5 Rate Limit Handling
• Meta API allows ~200 calls/hour per token. With 50 clients × 3 levels = 150 calls per sync cycle — well within limits
• Add usleep(200000) (200ms) between client syncs to be safe
• Parse X-Business-Use-Case-Usage header to detect approaching limits

7. Security Requirements

Concern
Implementation
Access Tokens
AES-256-CBC encrypted in DB; key stored only in .env (not in code)
Passwords
bcrypt hash, cost factor 12; no plain text ever stored
Session
PHP session with regenerate_id() on login; session timeout 8 hours
Client Isolation
Every DB query for dashboard data includes WHERE client_id = ? binding; no cross-client data leak possible
SQL Injection
PDO prepared statements everywhere; zero raw string interpolation in queries
XSS
htmlspecialchars() on all user-facing output; CSP header in .htaccess
CSRF
CSRF token in all POST forms (hidden input + session check)
.env Protection
.htaccess denies direct access to .env, includes/, cron/, db/
OAuth State Param
Random state string in session verified on OAuth callback to prevent CSRF on OAuth flow
Rate Limiting
Login: max 5 attempts per IP per 15 min (tracked in DB or APCu)

8. Cron Setup on Hostinger

8.1 Cron Configuration in hPanel
# Hostinger hPanel → Advanced → Cron Jobs → Add New
# Frequency: every 6 hours
0 */6 * * *   /usr/bin/php /home/u123456789/domains/panel.digitalrubix.com/public_html/cron/sync_all.php >> /tmp/metapanel_cron.log 2>&1
8.2 sync_all.php Logic
• Load all active clients from DB where active=1 AND meta_access_token IS NOT NULL
• For each client: call meta_api.php to pull last 90 days of data (first run) or last 7 days (subsequent)
• Upsert rows in ad_data_cache using INSERT ... ON DUPLICATE KEY UPDATE
• Write success/error row to sync_logs table
• On any Meta API error: log error, continue next client (non-blocking)
• Total execution time for 50 clients should be under 3 minutes
8.3 Hostinger-Specific Notes
• Use require_once $_SERVER["DOCUMENT_ROOT"] . "/includes/config.php" — never relative paths in cron
• Hostinger shared hosting has PHP 8.2 available — select it in hPanel → PHP Configuration
• Max execution time for cron: set via set_time_limit(300) inside sync_all.php
• File uploads (logos): use move_uploaded_file() to assets/logos/ — ensure 755 permissions
